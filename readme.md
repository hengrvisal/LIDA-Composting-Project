### **3. Architecture**

##### **a. Data Processing**

Aside from the basic data cleaning, an oversampling technique is implemented to compensate for the inadequate amount of data we're working with.

##### **b. Multioutput Regressor**

*Goal*: Predict the **future compost conditions** over time
*Inputs*:

- Sensor readings at time t (temperature, moisture, oxygen, CO2, methane, etc.).
- Historical lag values (previous steps).

*Outputs*:

- Forecasted temperatures for all probes (temperature_active1, temperature_active2, etc.).
- Expected **end date** of composting process (when system reaches a stable, low-temperature condition).

**How it works**:

1. A regression model (RandomForestRegressor with MultiOutputRegressor) learns to predict multiple target variables simultaneously.
2. The model is trained to predict the **next-step values** for each target.
3. During forecasting, the model rolls forward step-by-step:

    - Takes last known values
    - Predicts next step
    - Feeds prediction back as input for the following step
4. A compost "end date" is estimated by applying rules to the forecasted temperatures (e.g., stable for N consective days, below a threshold).

##### **c. Phase Detector**

*Goal*: Detect and predict **which phase** of composting the process is in (Active or Curing/Heating, Cooling, or Stable).
*Inputs*:

- Slopes of temperature trends (dervied via rolling regression)
- Sensor features (same set as forecaster).

*Outputs*:

- Current phase classification
- Next-step phase prediction
- Phase change flag (detects when a transition occurs).

**How it works**:

1. A rolling slope is calculated for temperature to capture the trend (rising, falling, stable).
2. These slope features are mapped into phase labels:

    - **Heating** if slope > threshold
    - **Cooling** if slope < threshold
    - **Stable** otherwise

3. A classifier (RandomForestClassifier) is trained on lagged features to predict the next phase.
4. A "phase change" is flagged whenever the predicted phase differs from the current phase.

##### **d. Architecture idea**

 The idea here is that the **forecaster** tells *what's coming* in terms of sensor values & compost completion, and the **phase detector** tells *where you are* in the compost lifecycle and detects transitions.

### **4. Technicalities**

##### **a. Dataset Schemes**

- Feature set (sensors): ```[moisture_active1, moisture_active2, oxygen, co2, temperature_curing1, temperature_curing2, moisture_curing1, moisture_curing2, methane, temperature_active1, temperature_active2, temperature_active3, temperature_active4]```.
- All features are cast to numeric ```(errors='coerce')```.
- Data are sorted by ```run_id```, ```time_stamp``` ("run_id" the simulated run cycle generated by the oversampler)

##### **b. Core configuration**

```
# fixed feature set (hardware-driven)
features = [
  'moisture_active1','moisture_active2','oxygen','co2',
  'temperature_curing1','temperature_curing2',
  'moisture_curing1','moisture_curing2','methane',
  'temperature_active1','temperature_active2','temperature_active3','temperature_active4'
]

# temps to forecast (multi-output)
TARGET_TEMPS = [
  'temperature_active1','temperature_active2','temperature_active3','temperature_active4',
  'temperature_curing1','temperature_curing2'
]

# lag steps (history length used as features)
LAGS = [1, 2, 3]

# phase labelling (from rolling slope on a core temp)
CORE_TEMP = 'temperature_active1'
SLOPE_HEAT = +0.2   # >= -> "heating"
SLOPE_COOL = -0.2   # <= -> "cooling"

```

##### **c. Label creation (phase & next-step targets)**

1. **Rolling slope** of ```CORE_TEMP``` over 5 steps (per ```run_id```).
2. Map slope -> phase: ```heating``` (>= SLOPE_HEAT), ```cooling``` (<= SLOPE_COOL), else ```stable```.
3. Shift by 1 to create **next-step** labels:
    - ```phase_next```
    - ```phase_change_next = (phase_next != phase)```
4. For each temp in ```TARGET_TEMPS```: create a next temp (next-step regression targets).

##### **d. Feature Engineering (lags; leakage-safe)

- build **lagged features** for all raw sensors (features + ```TARGET_TEMPS```) per ```run_id```:
- Drop rows that cannot form all lags or next-step targets.
- The reason behind **lags** is that they give the model revent history (momentum) while avoiding peeking at the future.

##### **e. Time-aware split**

- Train on **all runs except the last**; test on the **last run** preventing future leakage.

##### **f. Models**

1. Multi-output temperature forecaster (next-step)

    - Model: ```MultiOutputRegressor(RandomForestRegressor)```
    - Inputs: all lagged features
    - Targets: ```{temp}_next for temp in TARGET_TEMPS```
    - Save training feature order for inference
    - MAE on the holdout run for accuracy check

2. Phase Detector (2 options)

    - **Multiclass**: predict ```phase_next``` (heating, stable, cooling)
    - **Binary**: predict ```phase_change_next``` (0, 1)
    - Model: ```RandomForestClassifier(class_weight='balanced_subsample')```
    - Inputs: the same lag feature space
    - Metrics: classification report and confusion matrix

##### **g. Multi-step roll-forward simulation**

Purpose: produce a **future trajectory** of temperatures (and optional phases) for N days ahead.

1. **Seed** with the last ```max(LAGS)``` rows of the holdout run (raw sensors only).
2. For each future day:

    - Rebuild lag features from the growing buffer.
    - Reindex to ```FEATURE_ORDER_REG``` (and ```FEATURE_ORDER_CLS``` if used).
    - Predict all next temperatures -> append as the next raw row (non-temp sensors held constant for row).
    - Optional: predict ```pred_phase_next```

3. Collect into ```future_multi``` with columns
4. Plotting

##### **h. Expected end date (multi-output)**

Compute per-probe and overall expected end dates from ```future_multi```.

**Rules (options)**

- Rule A (ambient-based): temp <= ```ambient + delta_c``` for ```K``` consecutive days and not heating.
- Rule B (absolute): temp <= ```abs_thresh_c``` for ```K``` consecutive days and not heating.

**Functions** returns:

- a table of ```[temp_next_col, end_idx, end_date, rule_used]``` per probe
- an **overall end date** selected by policy:
  - ```"all"``` (strict- latest of all probe dates),
  - ```"any"``` (optimistic - earliest),
  - ```"majority"``` (robust - median)

**Tuning is still required in this stage**

##### **i. Execution Order (at inference time)**

```text
seed last max(LAGS) rows  
→ for each future day:
    build lag features
    → forecaster predicts next temperatures (multi-output)
    → (optional) classifier predicts next phase
    → append predicted temps to buffer (non-temps constant)
    → mark phase change points

after N days:
    compute per-probe & overall expected end dates from forecast
    → plot temps with phase markers and end-date lines
```

##### **j. Common pitfalls & fixes**

- Feature order mismatch: Save and reuse ```FEATURE_ORDER_REG/CLS```; ```reindex(columns=..., fill_value=np.nan)``` before ```predict()```
- Duplicate base columns: when building lags, dedupe ```base_cols``` with ```list(dict.fromkeys(...))``` so ```shift()``` always returns a Series.
- Index alignment errors: when assigning rolling slopes per run, write with ```df.loc[g.index, 'col'] = values```.
- Too-good scores: Next-step temp is easy (autocorrelation). Evaluate **multi-day** rollouts. Make phase detection harder by:

  - predicting ```phase_change_next``` (binary)
  - defining phase from **multiple signals**, nor only the same temperatue predicted.

##### **k. Knobs to tune for your bin**

- ```LAGS``` history length
- slope thresholds: ```SLOPE_HEAT```, ```SLOPE_COOL```
- end-date thresholds: ```delta_c```, ```abs_thresh_c```, ```consecutive_days```, ```overall_policy```
- which temps are in ```TARGET_TEMPS``` and which count as "core" for completion

##### **l. Extensions (nice next steps)**

- Forecast **moisture/O2/CO2** too (their own regressors or another multi-output block) and roll them forward.
- Use ambient from a **weather feed** to enable Rule A.
- Train **phase detector** on human labels if available.
- Swap RandomForest for an LSTM/TCN for better multi-step accuracy.
- Add an **MPC** loop that proposes ventilation/mixing actions from forecasts.
